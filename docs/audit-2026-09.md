## B1 — the donation counter reads 0.00 in a background tab

**`app/components/FundContext.jsx`.** The displayed number is eased toward its
target with `requestAnimationFrame`. A hidden tab never fires one, and the
effect's dependency array is `[target]` — which does not change when the tab
becomes visible. So the animation is never started and never retried.

Confirmed on production: `visibilityState: "hidden"`, `rafFired: false`, amount
stuck at `0.00SOL`.

Middle-clicking a link, "open in new tab", or clicking through from a thread
while reading something else are all ordinary. Every one of them shows the
headline number of the entire project as **zero**, for the whole session, and
the badge next to it says "PREVIEW — DEMO DATA" which makes it read as a
deliberate statement that nothing has been raised.

**Fix:** treat the animation as an enhancement, not as the source of the value.
Render the target if the animation has not run, and re-run on
`visibilitychange`.

## S1 — the sign-in domain is taken from the request

**`app/api/auth/verify/route.js`** and **`app/api/auth/nonce/route.js`** both do:

```js
const domain = new URL(request.url).host;
```

The message is then built with `Domain: ${domain}`, and the comment above it
says exactly why that field exists:

> A signature that says only "prove you own this wallet" can be collected by any
> site and replayed here. Binding the domain … means a signature phished
> elsewhere is a signature for somewhere else.

That argument only holds if the server knows which domain it *is*. Reading the
host from the request means the server binds to whatever hostname the attacker
used to reach it, and the app is reachable under more than one — every Vercel
deployment URL is public and routable.

**The attack:** request a nonce for the victim's address through
`tubby-….vercel.app`; phish the victim into signing "tubby-….vercel.app wants
you to sign in with your Solana account: … Nonce: N" on a page you control;
POST the signature back to `/api/auth/verify` with that Host. The server
rebuilds the identical message, ed25519 verifies, and a session cookie is
issued for the victim's wallet.

Nothing else in the chain stops it: the nonce is legitimately issued, unburned,
and inside its TTL.

**Fix:** pin the accepted domain server-side (an env var, or a constant list),
compare the request host against it, and reject anything not on it. The domain
in the signed message must be a value the server chose, never one the caller
supplied.

## D1 — EXIF survives into the published photos

Seven files under `/public/cares/` carry 7–14 KB of EXIF each. There is no GPS
in this batch. There **is** an embedded JPEG thumbnail in each one — a copy the
camera made at capture time, which resizing does not regenerate.

I carved the thumbnails out of the live files and looked at them. **All of them
show the hearts already applied**, so nothing leaked. That was the editing app
re-saving the thumbnail, not anything the pipeline did.

The next delivery, redacted in a different app, can ship an un-redacted face
inside a file whose visible pixels are covered. This is a well-worn way for
"redacted" images to be un-redacted, and the whole reason the photo rules in
`tubby-cares.md` §5 exist.

**Fix:** add `-strip` to the ImageMagick step and make it a rule beside the
photo rules, so it is not a thing anyone has to remember.

## S2 — the rate limiter loses a race

**`lib/server/guard.js`**, `rateLimit()`. On a window collision it reads the
row, adds one in JavaScript, and writes it back:

```js
const row = await db.one("rate_limits", `${q}&select=count`);
const count = (row?.count ?? 0) + 1;
if (count > max) throw userError(…, 429);
await db.update("rate_limits", q, { count });
```

Two requests that read the same value both write the same value. The counter
undercounts by exactly the concurrency, so the cap is bypassed by sending
requests in parallel — which is how an attacker sends them.

The file's own comment is right that an in-memory limiter resets on a cold
start. The database fixed durability and left atomicity.

**Fix:** a Postgres function doing `update … set count = count + 1 returning
count`, called with `service_role`, so the increment and the read are one
statement.

## B2 — four dead links on /tokenomics

Live right now: **View fee config**, **Delivery log**, **Updates** and **Bite
log** all render with `href="#"`.

The home page hides unfilled links through `isReal()`; `/tokenomics` never got
the helper and renders `config.links.*` unguarded. The home page has zero dead
links; this page has four — and it is the page whose own strip reads "Don't
trust the pie — audit it."

**Fix:** the same `isReal()` guard, applied on `/tokenomics`.

## C1 — the cause is described four different ways

| Where | Wording |
|---|---|
| hero | "orphanages and children's care centres in Brazil" |
| Cares section, tokenomics, footer, marquee (8 hardcoded places) | "children's shelters in Rio de Janeiro" |
| `config.care.cause` | "children's homes and care institutions in Rio de Janeiro" |
| the institution actually named | "a residential care institution for people with disabilities" |

Two problems.

**The word "orphanages" is not accurate for the partner we name.** Lar Maria de
Lourdes is an *instituição de acolhimento para pessoas com deficiência*. A
hostile reader who clicks the link we ourselves provide finds that out in one
step, and "they don't know who they're donating to" is a cheap shot we handed
over.

**`config.care.cause` is dead config.** Nothing reads it; the string is
hardcoded in eight places instead, so changing the cause means finding all
eight.

**Fix:** one wording, decided once, read from `care.cause` everywhere.

## S3 — `issuedAt` is signed and never checked

The login message carries `Issued At: …` and the server never validates it —
not the format, not the age. Freshness is genuinely enforced by the nonce TTL,
so this is not exploitable. It is listed because a reader auditing the message
will assume the field does something, and because the day the nonce TTL is
relaxed it silently becomes the only freshness check, and it is not one.

## S4 — `int()` accepts things that are not integers

`Number.isInteger(Number(v))` passes for `true` (1), `[]` (0), `["5"]` (5),
`null` (0) and `""` (0). Bounds contain the damage, and no current caller can
be pushed anywhere interesting by it. Worth tightening to a real numeric check
before anything priced in money uses it.

## Checked and sound — no action

These were attacked and held, and are recorded so the next audit does not
re-litigate them.

- **RLS.** Every table gets `enable row level security` **and** `force row level
  security` **and** `revoke all … from anon, authenticated`. Two independent
  failures, not one. Verified live: the public key reads nothing and writes
  nothing on all 18 tables.
- **Sessions.** httpOnly + Secure in production + SameSite=lax; the token is
  stored as a SHA-256 hash, so a database dump is not a stack of working
  logins. The player id comes from the cookie and never from the body — there
  is no code path where a client-supplied id chooses whose town changes.
- **Nonce ordering.** The nonce is burned *before* the signature is checked, so
  two concurrent attempts cannot both win and the database decides the race.
- **Concurrency on town writes.** An optimistic `version=eq.${row.version}`
  guard; a losing write changes nothing and the gacha roll it would have
  produced is discarded rather than recorded.
- **Idempotency.** Keys are released on failure, so a failed intent does not
  permanently replay "nothing happened" to the player retrying it.
- **Error handling.** Exposure is opt-in per error; the comment records a real
  past leak (a PostgREST 400 naming a table and column) and the fix.
- **Secrets.** Nothing sensitive is committed; `.env.local` is ignored;
  `lib/server/db.js` refuses to run if the service key appears in any
  `NEXT_PUBLIC_` variable, checked on every cold start including production.
- **XSS surface.** No `dangerouslySetInnerHTML` anywhere. Nothing a player types
  is rendered — no names, no labels, no chat. This is why the CSP is currently
  allowed to sit at `'self' 'unsafe-inline'`: the trigger written into
  `middleware.js` for returning to a nonce has genuinely not been reached yet.
- **Links.** Every `target="_blank"` carries `rel="noopener noreferrer"`.
- **Buy buttons.** Correctly inert while `live: false`, with `aria-disabled` and
  no href.
